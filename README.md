# Telegram-бот Финансового факультета

Рабочий Telegram-бот для Финансового факультета Финансового университета:
информация о факультете и Студенческом совете, документация в PDF, приём и
обработка обращений студентов, админ-панель прямо в Telegram (без правки
кода для обновления контента).

Стек: **Python 3.11+, aiogram 3.x, SQLAlchemy 2.0 (async), SQLite/PostgreSQL**.

---

## 1. Структура проекта

```text
├── bot/
│   ├── main.py                 # точка входа
│   ├── config.py               # чтение .env
│   ├── handlers/
│   │   ├── user/               # /start, "О факультете", "Студсовет", "Документация", fallback
│   │   ├── requests/           # сценарий подачи обращения студентом
│   │   └── admin/              # /admin и вся админ-панель
│   ├── keyboards/              # inline/reply клавиатуры
│   ├── states/                 # группы состояний FSM
│   ├── database/               # модели, engine, репозиторий (crud.py), seed.py
│   ├── services/               # уведомления студенту / в рабочую группу
│   └── utils/                  # IsAdmin-фильтр, callback_data, форматирование, middleware
├── run.py                      # запуск из корня проекта
├── Dockerfile                  # production-образ бота
├── docker-compose.yml          # запуск контейнера через Docker Compose
├── .dockerignore               # исключения из Docker build context
├── requirements.txt
├── .env.example
└── README.md
```

## 2. Установка

Требования: Python 3.11+, доступ в интернет для установки зависимостей.

```bash
git clone <ваш-репозиторий>
cd <папка-проекта>

python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt
```

Драйверы SQLite и PostgreSQL уже включены в `requirements.txt`.

## 3. Настройка `.env`

Скопируйте пример и заполните значения:

```bash
cp .env.example .env
```

| Переменная         | Обязательна | Описание                                                                 |
|--------------------|:-----------:|---------------------------------------------------------------------------|
| `BOT_TOKEN`        | да          | Токен бота от [@BotFather](https://t.me/BotFather)                       |
| `DATABASE_URL`     | нет         | Строка подключения. По умолчанию — локальный SQLite-файл                 |
| `WORK_GROUP_ID`    | да          | ID Telegram-группы, куда приходят обращения студентов                    |
| `WORK_GROUP_THREAD_ID` | нет     | ID темы супергруппы; без него обращения идут в общую тему |
| `INITIAL_ADMIN_ID` | нет*        | Telegram ID начального администратора(ов) через запятую                  |
| `LOG_LEVEL`        | нет         | `DEBUG` / `INFO` / `WARNING` / `ERROR` (по умолчанию `INFO`)              |

\* Технически не обязательна, но без неё в системе не будет ни одного
администратора и панель `/admin` будет недоступна никому. Настоятельно
рекомендуется задать хотя бы один ID.

**Как узнать нужные ID:**

- **Свой Telegram ID** (для `INITIAL_ADMIN_ID`) — напишите боту
  [@userinfobot](https://t.me/userinfobot), он пришлёт ваш числовой ID.
- **ID рабочей группы** (`WORK_GROUP_ID`) — создайте группу, добавьте туда
  вашего бота **как администратора** (иначе он не сможет писать в группу и
  редактировать свои сообщения), затем добавьте временно
  [@getmyid_bot](https://t.me/getmyid_bot) либо посмотрите обновления через
  `https://api.telegram.org/bot<TOKEN>/getUpdates` после того, как кто-то
  напишет в группе — там будет `chat.id`. Для супергрупп ID отрицательный и
  начинается с `-100...`, вводите его в `.env` как есть, со знаком минус.

- **ID темы** (`WORK_GROUP_THREAD_ID`) — после первого запуска отправьте
  команду `/ids` прямо в нужной теме. Бот выведет готовое значение
  `WORK_GROUP_THREAD_ID`.

**Никогда не коммитьте `.env` в git** — файл уже должен быть в `.gitignore`
(добавьте, если её ещё нет: `echo ".env" >> .gitignore`).

## 4. Инициализация базы данных и первого администратора

Отдельная миграция не требуется — таблицы создаются автоматически при
первом запуске (`init_db()` в `main.py`). Начальные администраторы из
`INITIAL_ADMIN_ID`, стандартные тексты (история факультета, инфо о
Студсовете, текст об отборе) и текущий состав руководителей Студсовета
заполняются автоматически через `database/seed.py` — тоже при первом
запуске.

Если нужно только создать/наполнить БД без запуска бота (например, для
проверки перед стартом):

```bash
cd bot
python3 -m database.seed
```

Скрипт идемпотентен — повторный запуск не создаст дубликатов.

### Добавление ещё одного администратора позже

Все 4 (и более) администратора имеют одинаковые права. Управлять списком
можно прямо в боте: `/admin` → **🔐 Администраторы** → **➕ Добавить
администратора** (нужен только Telegram ID нового администратора — его
можно узнать, например, через [@userinfobot](https://t.me/userinfobot)).
Там же доступно удаление — с защитой: удалить последнего администратора
невозможно, чтобы никто не остался без доступа к панели.

`INITIAL_ADMIN_ID` в `.env` по-прежнему используется только при самом первом
запуске (или если понадобится восстановить доступ, добавив ID и
перезапустив бота — seed не создаёт дубликатов для уже существующих
администраторов).

## 5. Запуск

Из корня проекта:

```bash
python3 run.py
```

Или из папки `bot/`:

```bash
cd bot
python3 main.py
```

При старте бот:
1. поднимает соединение с БД и создаёт таблицы, если их ещё нет;
2. выполняет seed (админы из `.env`, стандартные тексты, состав Студсовета);
3. запускает long polling.

Если запускаете бота на сервере **без Docker**, используйте systemd для
автоперезапуска. Пример unit-файла:

```ini
[Unit]
Description=Fin Faculty Telegram Bot
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/fin_faculty_bot/bot
ExecStart=/opt/fin_faculty_bot/venv/bin/python3 main.py
Restart=on-failure
EnvironmentFile=/opt/fin_faculty_bot/.env

[Install]
WantedBy=multi-user.target
```

## 6. Запуск в Docker на сервере

Ниже полный порядок первого запуска на чистом сервере. Бот работает через
Telegram long polling, поэтому открывать входящие порты не нужно.

### Шаг 1. Проверить Docker

На сервере должны быть установлены Docker Engine и Docker Compose plugin.

```bash
docker --version
docker compose version
```

Обе команды должны вывести версию без ошибок.

### Шаг 2. Скачать проект

```bash
git clone <URL-репозитория>
cd <папка-проекта>
```

Все следующие команды выполняются из корня проекта, где лежит `docker-compose.yml`.

### Шаг 3. Создать `.env`

```bash
cp .env.example .env
```

Откройте `.env` и заполните минимум три значения:

```dotenv
BOT_TOKEN=1234567890:replace_with_real_token
WORK_GROUP_ID=-1001234567890
WORK_GROUP_THREAD_ID=
INITIAL_ADMIN_ID=123456789
LOG_LEVEL=INFO
```

- `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
- `WORK_GROUP_ID` — ID рабочей супергруппы со знаком минус.
- `INITIAL_ADMIN_ID` — Telegram ID первого администратора.
- `WORK_GROUP_THREAD_ID` пока можно оставить пустым и заполнить после первого запуска.
- `DATABASE_URL` для SQLite указывать не нужно: Compose сам задаст путь к базе в volume.

**Важно:** не добавляйте `.env` в Git. Файл с секретами уже добавлен в `.gitignore` и
исключён из Docker-образа через `.dockerignore`.

### Шаг 4. Добавить бота в рабочую супергруппу

Добавьте бота в группу как администратора. Ему нужны права на отправку сообщений и
редактирование своих сообщений. Если группа использует темы, создайте нужную тему заранее.

### Шаг 5. Собрать и запустить бота

```bash
docker compose up -d --build
```

Compose автоматически:

- соберёт Python-образ;
- создаст контейнер `fin-faculty-bot`;
- создаст volume `fin-faculty-bot-data`;
- создаст таблицы SQLite и начальный контент;
- запустит Telegram polling в фоновом режиме;
- включит автозапуск после перезагрузки сервера.

### Шаг 6. Проверить запуск

```bash
docker compose ps
docker compose logs --tail=100 bot
```

В `docker compose ps` сервис `bot` должен иметь статус `Up`. В логах должно появиться:

```text
Бот запускается (polling)...
```

Для непрерывного просмотра логов:

```bash
docker compose logs -f bot
```

Выход из просмотра логов по `Ctrl+C` не останавливает контейнер.

### Шаг 7. Указать ID темы супергруппы

Если обращения должны приходить в определённую тему:

1. Отправьте `/ids` прямо в нужной теме.
2. Скопируйте значение `WORK_GROUP_THREAD_ID` из ответа бота.
3. Запишите его в `.env`:

   ```dotenv
   WORK_GROUP_THREAD_ID=12345
   ```

4. Пересоздайте контейнер, чтобы он получил новое значение:

   ```bash
   docker compose up -d --force-recreate
   ```

База при этом не удалится, потому что она хранится в volume.

### Шаг 8. Проверить бота в Telegram

1. Напишите боту `/start` в личном чате.
2. Откройте `/admin` от имени администратора из `INITIAL_ADMIN_ID`.
3. Отправьте тестовое обращение.
4. Убедитесь, что оно пришло в нужную тему рабочей супергруппы.
5. Проверьте кнопки «Ответить» и «Закрыть».

### Повседневные команды

```bash
# Статус
docker compose ps

# Логи
docker compose logs -f bot

# Перезапуск
docker compose restart bot

# Остановка и запуск
docker compose stop
docker compose start

# Удалить только контейнер; база останется
docker compose down
```

### Обновление кода

```bash
git pull
docker compose up -d --build
docker compose logs --tail=100 bot
```

Образ и контейнер будут обновлены, а SQLite-база останется в volume.

### Хранение SQLite

- имя volume: `fin-faculty-bot-data`;
- путь к базе внутри контейнера: `/app/data/fin_faculty_bot.db`;
- `docker compose down`, пересборка и перезагрузка базу не удаляют;
- **`docker compose down -v` удалит volume и всю базу безвозвратно**.

### PostgreSQL (опционально)

Для внешней PostgreSQL укажите в `.env`:

```dotenv
DATABASE_URL=postgresql+asyncpg://user:password@db-host:5432/fin_faculty_bot
```

Затем пересоздайте контейнер:

```bash
docker compose up -d --force-recreate
```

`localhost` внутри контейнера — это сам контейнер, поэтому для внешней БД
используйте её сетевое имя или IP-адрес.

### Перенос уже существующей SQLite-базы из старого контейнера

Если бот уже работал без volume и в базе есть данные, не запускайте сразу
`docker compose up`. Сначала остановите бота и скопируйте базу:

```bash
docker compose stop bot
docker cp fin-faculty-bot:/app/fin_faculty_bot.db ./fin_faculty_bot.db.backup
docker compose build
```

Затем поместите копию в новый volume от имени root и верните владельца файла:

```bash
docker compose run --rm --user root \
  -v ./fin_faculty_bot.db.backup:/backup.db:ro \
  bot sh -c 'cp /backup.db /app/data/fin_faculty_bot.db && chown appuser:appuser /app/data/fin_faculty_bot.db'

docker compose up -d
```

После проверки бота файл `fin_faculty_bot.db.backup` можно удалить вручную.

## 7. Хранение файлов (фото, PDF)

Бот не сохраняет файлы на диск — вместо этого используется `file_id`,
который выдаёт Telegram при получении файла. Telegram сам хранит файл на
своих серверах, а `file_id` в БД позволяет отправить его снова в любой
момент. Это самое простое и надёжное решение для такого масштаба проекта —
не нужно ни файлового хранилища, ни backup-стратегии для бинарных файлов.

## 8. Структура основных таблиц БД

| Таблица                 | Назначение                                                                 |
|--------------------------|-----------------------------------------------------------------------------|
| `users`                 | Все пользователи, писавшие боту (нужно для истории обращений)              |
| `admins`                | Администраторы бота, авторизация строго по `telegram_id`                    |
| `requests`               | Обращения студентов: анонимность, курс, корпус, текст, статус, ответственный админ, ответ, время создания/взятия в работу/закрытия |
| `content_sections`       | Редактируемые тексты по ключу: история факультета, инфо о Студсовете, инфо об отборе |
| `faculty_admins`         | Администрация факультета: ФИО, должность, фото, контакты                    |
| `student_organizations` | Студенческие организации/комитеты/творческие коллективы по категориям      |
| `council_leaders`        | Руководители Студенческого совета                                          |
| `digests`                 | Дайджесты мероприятий по месяцам                                            |
| `documents`               | PDF-документы: название, описание, `file_id`                               |

Обращение (`requests`) хранит статус (`NEW` / `IN_PROGRESS` / `CLOSED`),
`user_id` — техническую связь с автором, которая сохраняется **даже при
анонимном обращении** (это нужно, чтобы бот мог доставить ответ). Поле
`is_anonymous` влияет только на то, что видят администраторы в рабочей
группе — их username/ID там не показывается.

## 9. Команды бота

| Команда   | Кто может использовать | Что делает                              |
|-----------|--------------------------|-------------------------------------------|
| `/start`  | все, только в личном чате | Приветствие + главное меню                |
| `/menu`   | все, только в личном чате | Открыть главное меню заново (если сценарий завис) |
| `/admin`  | админы, только в личном чате | Открыть админ-панель                      |
| `/ids`    | все, в любом чате          | Показать ID пользователя, чата и темы     |

В группах бот публично отвечает только на `/ids`. Пользовательское меню,
команды `/start` и `/menu`, а также `/admin` работают только в личном чате.
Админские inline-кнопки под обращениями в рабочей теме продолжают работать.

## 10. Административные функции

Через `/admin` доступны:

- **📝 Управление информацией**
  - Тексты (история факультета, инфо о Студсовете, инфо об отборе) —
    просмотр и редактирование с предпросмотром перед сохранением;
  - Администрация факультета — добавление, **полное редактирование** (ФИО,
    должность, контакты, фото — включая замену и удаление фото по
    отдельности), **включение/выключение видимости** для студентов без
    удаления записи, удаление;
  - Студенческие организации — добавление, **полное редактирование**
    (категория, название, описание, ссылка), **включение/выключение
    видимости**, удаление. Категория задаётся произвольным текстом — новые
    категории не требуют изменения кода.
- **📚 Управление документацией** — добавление PDF с названием и описанием,
  редактирование названия/описания, замена файла, удаление.
- **📨 Обращения студентов** — статистика по обращениям (всего, новых, в
  работе, закрыто, анонимных/неанонимных). Сама обработка обращений
  (взятие в работу, ответ, закрытие) происходит прямо под сообщением
  обращения в рабочей группе, и её может выполнять **только назначенный
  администратор** — см. раздел 14 ниже.
- **📅 Дайджест мероприятий** — создание, редактирование текста, удаление.
- **👥 Руководители Студсовета** — добавление, **полное редактирование**
  (ФИО, должность, Telegram username, фото — замена/удаление),
  **включение/выключение видимости**, удаление.
- **🔐 Администраторы** — список текущих администраторов, добавление
  нового по Telegram ID, удаление. Систему защищена от удаления последнего
  администратора (см. раздел 14).

Все администраторы имеют одинаковые полные права на все перечисленные
функции — ролей `superadmin`/`admin`/`moderator` нет и не предполагается.
Доступ проверяется по Telegram ID на каждом действии, а не только при входе
в `/admin`.

### UX редактирования существующих записей

Для администрации факультета, студенческих организаций и руководителей
Студсовета редактирование одного поля выглядит одинаково:

```
Открыть запись → ✏️ Изменить → выбрать поле → ввести новое значение →
предпросмотр → ✅ Сохранить / ❌ Отменить
```

Видимость для студентов переключается отдельной кнопкой прямо на карточке
записи (`👁 Показывать пользователям` / `🚫 Скрыть от пользователей`) и не
требует подтверждения — это обратимое действие. Удаление записи остаётся
отдельным, явным действием с кнопкой `🗑 Удалить`.

## 11. Что нужно заменить/добавить перед production-запуском

Согласно ТЗ, часть контента намеренно оставлена как понятный placeholder,
чтобы не придумывать несуществующую информацию. Перед вводом бота в
эксплуатацию нужно через админ-панель добавить:

- **Администрацию факультета** — ФИО, должности, фото, контакты (кроме
  телефона декана — он намеренно не публикуется) на основе
  `https://www.fa.ru/university/structure/scientific-educational-departments/ff/HeadsFaculty/`;
- **НСО Финансового факультета** и описания комитетов (КВС, УСК, ИК, ПК) —
  заготовки-категории уже созданы, но без содержательного описания;
- **Клуб молодого финансиста** и **Предпринимательский клуб** — созданы как
  неактивные (`is_active=False`), т.к. их существование требует
  подтверждения; включить и заполнить после уточнения у заказчика;
  проще всего — удалить старую запись через админку и добавить заново с
  `is_active=True` (по умолчанию новые записи активны);
- **Фотографии руководителей Студенческого совета** — состав уже загружен
  из ТЗ (ФИО, должности, username), фото нужно добавить отдельно;
- **PDF-документы** — «Папка спасения (НПБ)», заявления из деканата и
  прочие материалы с сайта Финуниверситета / Google Drive Координаторства;
- Заполнить реальные `BOT_TOKEN`, `WORK_GROUP_ID` и, если используются
  темы, `WORK_GROUP_THREAD_ID` в `.env`, добавить в
  рабочую группу бота с правами администратора (нужны, чтобы редактировать
  сообщения при смене статуса обращения).

## 12. Безопасность — что уже реализовано

- Администраторы определяются строго по `telegram_id`, никогда по username.
- Права проверяются на каждом административном действии (и в командах, и в
  callback), а не только при входе в `/admin` — это реализовано через
  `utils/admin_filter.IsAdmin`, применённый как фильтр ко всем admin-роутерам.
- Личность автора анонимного обращения не попадает в текст, отправляемый в
  рабочую группу; администратор не видит username/ID/имя.
- **Взятие обращения в работу выполняется атомарно на уровне СУБД** —
  `crud.take_request` выполняет один SQL-запрос
  `UPDATE requests SET status='IN_PROGRESS', admin_id=:id WHERE id=:id AND status='NEW'`
  и определяет победителя гонки по `rowcount`, а не последовательностью
  `SELECT` → проверка в Python → `UPDATE` (которая не даёт гарантий при
  настоящем параллелизме). Проверено конкурентным тестом с несколькими
  одновременными `asyncio`-задачами и отдельными сессиями/транзакциями —
  см. раздел 14.
- **После взятия обращения в работу отвечать и закрывать его может только
  назначенный администратор.** Любой другой администратор, нажавший
  «Ответить» или «Закрыть обращение» на занятом обращении, получает
  предупреждение `🔄 Обращение уже находится в работе у другого
  администратора.` и не попадает в сценарий ввода ответа. Проверка
  выполняется как при взятии в работу, так и повторно непосредственно перед
  отправкой ответа (на случай, если обращение было переназначено/закрыто,
  пока администратор печатал текст).
- **Управление администраторами защищено от удаления последнего
  администратора** — проверка выполняется в `crud.delete_admin`
  (на уровне репозитория, а не только в UI), поэтому её невозможно обойти.
- Токен бота и все параметры окружения читаются из `.env`, нигде не
  захардкожены; `.env` не должен попадать в git.
- Пользовательский текст, попадающий в сообщения с `parse_mode=HTML`
  (например, текст обращения), экранируется (`utils/formatting.escape_html`),
  чтобы студент не мог сломать разметку или внедрить произвольный HTML.
- Любая непредвиденная ошибка ловится глобальным обработчиком
  (`utils/error_handler.py`) — пользователь получает понятное сообщение,
  а не traceback; всё логируется.

## 13. Известные ограничения MVP (и как их снять при необходимости)

- Обращение поддерживает только текст (без фото/файлов) — в ТЗ это
  сознательно оставлено для будущего расширения; для этого нужно добавить
  обработку `F.photo` / `F.document` в `handlers/requests/user_request.py`
  и хранение `file_id` в модели `Request`.
- Кнопки «Мои обращения» для студента нет — БД уже хранит всю историю
  (`requests.user_id`), достаточно добавить хендлер со списком обращений
  конкретного пользователя.
- Ответ администратора на обращение отправляется как обычное сообщение в
  той же рабочей группе (не личным сообщением боту) — так короче цепочка
  действий для админа. Состояние диалога (FSM) привязано к паре
  (чат, администратор), поэтому разные администраторы, отвечающие
  одновременно на разные обращения в одной группе, не мешают друг другу.
- Уведомление новому администратору о выдаче прав не отправляется
  автоматически — он видит доступ к `/admin`, как только его добавили, но
  бот не пишет ему об этом первым (Telegram не позволяет боту написать
  пользователю, который никогда не запускал с ним диалог). Стоит сообщить
  новому администратору о доступе лично.

## 14. Чек-лист тестирования (см. также ТЗ, раздел 39)

Как только заполните `.env` реальными значениями — пройдите вручную:

**Студент:** `/start` → каждый раздел меню → «Назад»/«Главное меню» →
неанонимное обращение → анонимное обращение → каждый курс → каждый корпус →
отмена обращения → получение ответа → получение уведомления о закрытии.

**Администратор:** `/admin` → каждый раздел админки → добавление контента →
**полное редактирование** каждого поля администрации факультета,
студенческих организаций и руководителей Студсовета → **включение/
выключение видимости** записи → **замена и удаление фото** → удаление
записи → добавление и замена PDF → получение нового обращения в группе →
взятие в работу → ответ → закрытие → управление администраторами (список,
добавление, удаление).

**Безопасность и блокировка обращений:** обычный пользователь не открывает
`/admin`; попытка вызвать admin-callback напрямую блокируется; анонимный
студент не раскрывается в группе; ответ приходит именно автору обращения;
секреты не в коде и не в git; **два администратора одновременно нажимают
«Ответить» на одно NEW-обращение — ровно один становится ответственным**;
**второй администратор не может ни ответить, ни закрыть обращение,
закреплённое за первым**; закрытое обращение нельзя обработать повторно;
**удалить последнего администратора невозможно**.

Все перечисленные сценарии (включая настоящую параллельную гонку двух и
трёх администраторов через `asyncio.gather` с отдельными сессиями БД, а не
последовательные вызовы) были воспроизведены и пройдены на этапе
разработки — см. историю изменений/тестовые прогоны в репозитории.
